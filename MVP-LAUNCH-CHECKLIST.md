## 8. WHOOP wearable integration (2026-08-27)

- [x] **Built — real OAuth 2.0, not a stub.** `server/services/whoopService.ts` + `server/routes/wearables.ts`: full authorization-code flow against WHOOP API v2 (connect → callback → token exchange → encrypted storage), a `/whoop/sync` route that pulls latest recovery/HRV/sleep/strain into `BiometricReading` (de-duped against repeat syncs), token refresh, and disconnect. OAuth `state` is HMAC-signed (derived from `JWT_SECRET`) so the callback can't be redirected to attach a stolen authorization to an arbitrary other patient. Frontend: `WhoopConnectCard` on the client dashboard with a real, required, separate consent checkbox (distinct from onboarding's PDPA consent — this is its own data-sharing purpose) before the connect button is even clickable, plus an OAuth-return landing page (`/client/wearables/callback`). All 4 locales translated.
- [x] **Token encryption at rest — added because this is real, not because anything else in this app does it.** `WearableConnection.accessToken`/`refreshToken` are now AES-256-GCM encrypted (key derived from `JWT_SECRET` via scrypt) before hitting the DB — the schema's own long-standing comment said "encrypted in real scenario"; this is that scenario, since these are live per-patient tokens granting access to real biometric data, unlike the shared `GEMINI_API_KEY`.
